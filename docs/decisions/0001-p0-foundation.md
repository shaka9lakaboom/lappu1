# 0001 — P0 foundation implementation decisions

- Status: accepted
- Date: 2026-09-25
- Scope: Phase P0 (foundation). None of these change the frozen architecture; they
  record how it was implemented and why.

## Context

P0 was rebuilt from scratch on branch `skillmirror-p0-rebuild`. The previous attempt
was not trusted: its project-state claimed CI and gates that did not exist, it decoded
JWTs without verifying signatures when no secret was set, let a signing-up client
choose its own role (including `admin`), and silently used placeholder Supabase URLs.

## Decisions

1. **Tool versions follow the current official templates, not the newest majors.**
   Next.js 16.3 / React 19.2 / Tailwind 4 / ESLint 9 / TypeScript 5 (as generated by
   `create-next-app@16.3.6`). TypeScript 7 and ESLint 10 exist but are not what the
   Next.js template targets.

2. **Next.js 16 `proxy.ts` instead of `middleware.ts`.** Middleware was renamed to
   Proxy in Next.js 16 (Node.js runtime by default). It refreshes the Supabase session
   cookie and guards `/dashboard`.

3. **Auth runs through Server Actions; no browser Supabase client at P0.** Sign up,
   sign in and sign out are server actions using `@supabase/ssr` cookie sessions. This
   keeps the production build free of secrets (CI builds without any Supabase env) and
   means no page touches Supabase at build time.

4. **Missing Supabase configuration fails loudly.** `readSupabasePublicEnv()` throws a
   `SupabaseEnvError` naming each missing variable. It also refuses a secret or
   service-role key placed in `NEXT_PUBLIC_SUPABASE_ANON_KEY`.

5. **Roles are a Postgres enum `app_role` (`STUDENT`/`TEACHER`/`ADMIN`) and are never
   client-writable.** The signup trigger always creates `STUDENT`; clients get column
   privileges only on `display_name` and `timezone`. Elevation is an operator action
   with the service role.

6. **Migrations are numbered `NNNN_name.sql`** (`0001_p0_foundation.sql`), which the
   Supabase CLI accepts as a version prefix. pgTAP tests live in `supabase/tests/`.

7. **Backend JWT verification supports asymmetric signing keys (JWKS) and legacy
   HS256.** Signature, `exp`, `aud=authenticated` and `iss=<SUPABASE_URL>/auth/v1` are
   always checked; there is no unverified fallback. When `SUPABASE_URL` is not set,
   protected routes fail closed with 503. No protected endpoint is exposed in P0
   (JWT-authenticated APIs are P1 work).

8. **`/health` is unversioned; `/v1` is mounted but empty.** Architecture section 13
   lists `GET /health` outside `/v1`. No `/v1/health` alias.

9. **`API_VERSION` is the service release version** reported by `/health`. The URL
   namespace `/v1` is fixed in code.

10. **The extension is bundled with esbuild, one self-contained file per entry.** MV3
    content scripts (P1) cannot load shared chunks, which Vite's multi-entry build
    produces. The P0 manifest requests no permissions and no host permissions.

11. **Extension loading is tested with Playwright's Chromium.** Branded Chrome no longer
    honours `--load-extension`; Playwright's Chromium loads `dist/` exactly as
    "Load unpacked" does, in CI as well as locally.

12. **CI runs the database and auth round trip against a local Supabase stack**
    started by the Supabase CLI from this repository's migrations. That proves the code
    paths but does not replace the P0 gate against the hosted project.

13. **The architecture document moved** from the repository root to
    `docs/architecture/` (a `git mv`, history preserved) to match the frozen layout.
